# Управляемое подключение серверов

Профиль C1 от 22.10.2026: SSH и Coolify Sentinel 1.1.2. Это не установка Coolify,
не управление приложениями и не backup runner. Prometheus остаётся отдельным
поддерживаемым способом мониторинга.

## Подключение

1. OWNER/ADMIN создаёт ресурс SERVER и открывает его карточку, «Управление сервером».
2. Указать SSH hostname/IP, порт и пользователя. Private network разрешать явно,
   только для доверенной сети. В Docker localhost означает контейнер InfraDeck.
3. Создать ключ. Добавить показанный публичный ключ в `authorized_keys` выбранного
   пользователя через существующий доверенный доступ/консоль провайдера. Это
   первоначальное разрешение доступа, а не ручное развёртывание агента. Без него
   приложение не может безопасно получить первый доступ к чужому серверу.
4. «Получить отпечаток»: авторизация ещё не выполняется. Сверить SHA256 host key
   с доверенной консолью сервера, например `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.
   Не подтверждать отпечаток только потому, что его показало приложение.
5. Ввести проверенный отпечаток, подтвердить ключ, выполнить проверку SSH.
   Характеристики Linux/архитектура/vCPU/RAM заполняются по фактическим данным.
6. Раскрыть установку Sentinel, прочитать изменения, ввести название сервера.
   Если Docker отсутствует, отдельно разрешить его установку. Для bootstrap
   поддержаны Ubuntu 22.04/24.04, Debian 12/13; нужен доступ к apt-репозиториям.
   При существующем Docker поддержан Linux amd64/arm64. Podman не заменяется.
7. Дождаться DONE, открыть «Метрики и графики». Сбор выполняет worker; очередь
   установки обрабатывает отдельный runner. При локальной разработке запустить
   `npm run worker` и `npm run runner`; Compose запускает оба автоматически.

Нужны root либо passwordless sudo, SFTP и работающий Docker daemon. Это сильные
права на удалённом сервере: используйте отдельного пользователя и доверенную сеть.
Устанавливается только фиксированный профиль; произвольного shell из UI нет.
Существующий Docker не обновляется и не перезапускается, прокси не устанавливается.
Первичная установка Docker может менять пакеты, службу и сетевые правила;
без отдельного checkbox она запрещена. Настройка firewall не реализована.

## Метрики И Ограничения

- Реальные CPU, RAM через MemAvailable, load15/vCPU из Sentinel; заполнение `/`
  через фиксированную read-only SSH-команду `df`. Нет host network, inode, iowait,
  контейнерных метрик, всех mount points или автоматического обнаружения сервисов.
- История CPU/RAM читается с сервера, графики 1/6/24 часа, максимум 4000 исходных
  точек и 1 MiB ответа, прореживание до примерно 600 точек. История не выдумывается.
  Sentinel хранит SQLite в своём каталоге 7 дней. История диска/load пока не выводится.
- Привязка источника к ресурсу создаётся автоматически. Обычные проектные права,
  правила CPU/RAM/DISK/LOAD и каналы email/Telegram/Discord применяются как для
  существующего мониторинга. Правила и внешние каналы администратор задаёт отдельно.
- Отсутствующие/устаревшие метрики не считаются нормой. RAM не принимается, если
  объём памяти агента не совпал с физическим объёмом, прочитанным через SSH.

## Изоляция И Секреты

Закреплён образ `ghcr.io/coollabsio/sentinel@sha256:1762968e066f516d94438ab01cb7366c9fb38bbaaa87ef612f7112855c8c3d14`
(1.1.2, amd64/arm64). Автообновления образа нет. Sentinel — Apache-2.0,
[исходный код и лицензия](https://github.com/coollabsio/sentinel).

Контейнер имеет `--network none`, read-only root, cap-drop ALL, no-new-privileges,
ограничения CPU/RAM/PID, tmpfs и ротацию логов. Нет опубликованных портов, Docker
socket и монтирования корня/процессов хоста. Единственный persistent mount — свой
каталог `/opt/infradeck-sentinel/<resource UUID>/db`. Env-файл рядом, каталог 700,
файл 600. API читается через SSH + docker exec и внутренний loopback.

В этой закреплённой версии host-only режим использует `DOCKER_HOST=/dev/null`:
без существующего пути upstream не стартует. Docker collectors будут недоступны;
это проверенный compatibility-профиль, не обещание поддержки произвольных будущих
версий Sentinel. Push/control plane/геолокация/traffic/storage collectors выключены.

Приватный SSH-ключ и случайный API-token зашифрованы существующим ENCRYPTION_KEY;
в браузер выдаётся только public key. Секреты и stdout/stderr удалённого выполнения
не пишутся в аудит/ошибки. Host key проверяется до авторизации; смена требует новой
осознанной проверки. Метаданные облака запрещены, DNS разрешается с фиксацией IP.
Runner не получает локальный Docker socket или root InfraDeck-хоста. Это отдельный
процесс, но не отдельный credential vault: у компонентов общий доступ к БД и ключу.

## Остановка, Отзыв И Удаление

«Отключить доступ InfraDeck» останавливает новые обращения и отменяет очередь;
не удаляет public key из authorized_keys и не останавливает агент автоматически.
Для полного отзыва удалите ключ на сервере доверенным каналом. В раскрытии
«Ротация SSH-ключа» подготовьте новую пару, введите имя сервера и подтвердите
add → verify → revoke. Runner добавляет новый public key через существующий доступ,
устанавливает отдельное соединение новым private key с прежним проверенным host
key, читает фиксированные facts и только после успеха удаляет прежний ключ.
Credentials переключаются атомарно. Поддерживается стандартный
`~/.ssh/authorized_keys` текущего SSH-пользователя, нужен Python 3. Чужие строки и
key options сохраняются. Symlink/hardlink/чужой owner/конкурентное изменение файла
прерывают операцию; запись через private temp + fsync + rename. Иные
AuthorizedKeysFile/AuthorizedKeysCommand и копии ключа в других местах не меняются.
При сбое pending private key остаётся encrypted: повтор сначала пробует новый
login, поэтому обрыв после отзыва старого не уничтожает путь восстановления.
Частичные изменения требуют проверки; DONE не записывается при отзыве прав.
Endpoint editing остаётся отдельной задачей. Private keys не показываются.

«Остановить Sentinel» требует название сервера, разрешено и при отключённом сборе.
Останавливается только контейнер с совпадающими workspace/resource labels. База
агента и env не удаляются. Автоматический uninstall/удаление Docker не выполняется.
Повторный запуск использует только свой контейнер с тем же digest; чужой не заменяется.

Активный SSH-доступ, установленный агент и QUEUED/RUNNING задания блокируют удаление
записи. Сначала остановить агент и отключить доступ, затем остальные зависимости.
При прерывании установки installed сохраняется консервативно: нельзя считать,
что удалённая команда ничего не изменила. Требуется успешная остановка.
Перед командами повторно проверяются актуальные права/версия/отзыв; watchdog
закрывает SSH при отзыве. Закрытие SSH не гарантирует откат уже запущенного apt:
после обрыва состояние необходимо проверить. Выполненные задания и безопасные
характеристики переходят в deletion snapshot, без ciphertext и env.

Backup/restore метаданных InfraDeck должен включать ENCRYPTION_KEY отдельно от БД.
SQLite агента на удалённом сервере не входит в metadata backup InfraDeck.
Мониторинг сам не запускает бэкапы. Отдельный [C2 executor](backups-s3.md) имеет
свою настройку/права/лимиты. Firewall не реализован. Статусы SSH ERROR/REVOKED и
agent STOPPED не подменяют свежесть сбора: collection отдельно DISABLED/STALE/OK.
