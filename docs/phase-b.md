## Настройка И Ручная Приёмка

1. Создать синтетический ресурс и политику бэкапа в «Бэкапы». Webhook не создаёт ресурс/политику автоматически и не запускает бэкап.
2. OWNER/ADMIN открывает «Источники», выбирает политику, название и срок подключения (не больше года). Сохранить показанный ключ в защищённой конфигурации внешнего скрипта: повторно прочитать его через UI/API нельзя. Endpoint отображается у подключения; resourceId взять из URL карточки ресурса `/infrastructure/<resourceId>`.
3. Записать результат в локальный JSON-файл, например в игнорируемый `data/backup-result.json`, без паролей, токенов и журналов внешней системы:

```json
{
  "externalRunId": "backup-host-a-20261020-001",
  "resourceId": "UUID-OF-THE-BOUND-RESOURCE",
  "status": "SUCCESS",
  "startedAt": "2026-10-20T10:00:00Z",
  "endedAt": "2026-10-20T10:05:00Z",
  "sizeBytes": "1048576"
}
```

4. Передать ключ через переменную окружения `INFRADECK_BACKUP_WEBHOOK_SECRET`, не через URL или аргументы команды. Выполнить:

```powershell
node scripts/send-backup-result.mjs http://localhost:3000/api/integrations/CONNECTION-ID/backup-runs data/backup-result.json
Remove-Item Env:INFRADECK_BACKUP_WEBHOOK_SECRET
```

За пределами loopback sender требует HTTPS. Ключ не выводится скриптом. Скрипт не запускается автоматически приложением; продукт не подключает корпоративные системы сам.

5. Первый запрос: HTTP 202; точный повтор файла с новым timestamp/signature: 200 и тот же ID. Изменить status, сохранив externalRunId: 409, прежний результат не изменяется. Для нового внешнего запуска нужен новый стабильный externalRunId.
6. В «Бэкапы» проверить `Webhook: <название>` и реальные даты/объём. SUCCESS не создаёт RestoreVerification. Новый PDF/XLSX включает результат; старые snapshots не меняются.
7. Проверить ротацию ключа, отказ со старой подписью, отзыв подключения и запрет VIEWER/OPERATOR. После перезагрузки страницы секрет не отображается. Активное подключение блокирует удаление политики/ресурса; после отключения удаление сохраняет историю результатов и квитанции приёма.

## Контракт И Защита

`POST /api/integrations/{connectionId}/backup-runs`, `Content-Type: application/json`. Схема и ответы: [openapi.yaml](openapi.yaml). API/session Bearer tokens не принимаются вместо подписи. Подключение жёстко ограничено одним workspace и одной политикой/ресурсом; payload не может выбрать другой workspace или policy.

`X-InfraDeck-Timestamp` содержит Unix seconds с допуском 300 секунд. `X-InfraDeck-Signature` равна `v1=` + lowercase hex HMAC-SHA256 от точных байтов `timestamp + '.' + body`. JSON не пересериализуется при проверке. Сравнение фиксированной длины выполняется через `timingSafeEqual`; см. [официальную документацию Node.js](https://nodejs.org/docs/latest-v24.x/api/crypto.html). Часы отправителя и InfraDeck должны быть синхронизированы.

Тело ограничено 16 KiB, в том числе при потоковой передаче без Content-Length; чтение ограничено 10 секундами. Принимаются только перечисленные поля, завершённые интервалы и SUCCESS/FAILED/UNKNOWN. Размер — десятичная строка в пределах signed BIGINT; неизвестные единицы не конвертируются. Результат является утверждением авторизованного отправителя, а не независимой проверкой целостности архива.

Ключ случайный 256-bit, хранится AES-256-GCM с внешним ENCRYPTION_KEY/keyVersion; показывается только при создании/ротации. Управление перепроверяет актуальную membership на сервере. Отзыв и приём сериализованы блокировкой строки подключения; после отзыва новых результатов нет. Дедупликация по connectionId/externalRunId и SHA-256 исходного тела предотвращает повторные записи при параллельной доставке. Изменённый результат с прежним externalRunId отклоняется, а не перезаписывает историю. Лимит — 120 успешных аутентифицированных запросов в минуту на подключение, включая точные повторы. Невалидные/отклонённые транзакции не меняют результат.

При сетевой неопределённости повторить те же байты с новой подписью/временем. Receipt, результат, lastReceivedAt, безопасный аудит и operational event сохраняются одной транзакцией. Секрет и тело запроса не попадают в audit/events. Дополнительных Redis jobs нет: это запись полученного статуса, не исполнитель операций.

## История И Эксплуатация

Включённая привязка, даже с истёкшим ключом, требует явного отключения перед удалением политики/ресурса. После удаления отключённое подключение сохраняется с policyId=null, а квитанции сохраняют прежний runId без обязательного FK на живой результат. Финансовая/операционная история переносится по [правилам удаления](deletion.md), вместе с безопасными метаданными привязок, без ciphertext. Отдельно исправленные/удалённые результаты также остаются в аудите/истории; квитанция не даёт повторно создать старый запуск.

Автоматического purge квитанций/подключений нет. Они включены в metadata backup; ENCRYPTION_KEY хранится отдельно и необходим для приёма после восстановления. Ротация signing key одного подключения не меняет глобальный encryption key. Объём PostgreSQL растёт с числом результатов; настройте ingress rate/body limits и защищённый backup retention. Не публикуйте endpoint без HTTPS.

Проверки выполняются на синтетических объектах отдельной временной БД и очереди командой `npm.cmd run test:phase-a` после production build. Прогон включает регрессии A и новые тесты B, несмотря на историческое имя команды.

Итог 20.10.2026: typecheck, lint, production/Docker build, семь миграций на чистой БД, 16 domain/database-тестов и 3 E2E прошли. Отдельно пройдены чистый Compose setup с worker/PDF, metadata backup/restore и read-only smoke текущего экземпляра. Проверены UTC-срок в PostgreSQL и desktop/mobile без горизонтального переполнения. Существующие рабочие объекты не удалялись, новые подключения к корпоративным системам не создавались.
