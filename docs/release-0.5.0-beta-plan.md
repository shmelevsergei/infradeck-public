## 1. Версия и результат

Целевая первая публикация: **`0.5.0-beta.1`**, Git tag **`v0.5.0-beta.1`**,
название для пользователя **InfraDeck 0.5.0 Beta 1**.
Исправления до принятия Beta: `0.5.0-beta.2`, далее по необходимости.
Версию `0.5.0` без prerelease-суффикса не публиковать до отдельного решения.
Это версия до 1.0: совместимость и миграции документировать явно, не обещать
стабильный публичный API только на основании номера.

Цель: воспроизводимо установить и обновить self-hosted InfraDeck из проверенного
набора артефактов, восстановить его данные/секреты, пройти ручную приёмку и
выпустить честно ограниченную Beta. Не увеличивать функциональность ради номера.
При составлении плана package.json содержал `0.1.0`; 23.10 идентификаторы кандидата согласованы как `0.5.0-beta.1`.

## 2. Исходное состояние

| Область | Факт | Что не считать завершённым |
| --- | --- | --- |
| A | Реестр, проекты, расходы, импорт, ручной учёт, отчёты, роли и история работают | Не переделывать эти сценарии ради релиза |
| B | Проектные права/бюджеты, Prometheus API, TLS, Alertmanager, SMTP/Telegram/Discord и outbox реализованы | Полная внешняя приёмка B открыта |
| Telegram | Реальный тест принят Telegram; пользователь подтвердил получение | Это один канал и test-message, не весь incident/recovery pipeline |
| Sentinel | Есть подключённый рабочий сервер и реальные метрики/история | Этот сервер не является разрешённой целью install/STOP/rotation/backup тестов |
| C1 | Restricted runner, host trust, install/STOP, add → verify → revoke SSH rotation | Полный внешний bootstrap/rotation/отказ/restart сценарий не принят |
| C2 | Ограниченный engine v1, S3, queue/schedule/retry/cancel/retention, isolated restore | Полная внешняя приёмка на согласованном source/S3/restore ещё открыта |
| D | Не реализован | Не включать firewall, управляемые обновления и произвольные remote changes в Beta |
| E | Есть прежние installer/Compose/metadata backup и инструкции | Нужна приёмка окончательных релизных образов; весь E ещё не закрыт |

Последняя зафиксированная полная регрессия: 23 domain/DB теста, 7 E2E и
14 clean migrations. Typecheck/lint/Next production build проходили; после неё
добавлены небольшие подсказки по allowlist и безопасная диагностика ошибок.
Эти результаты — база для повторной проверки, не сертификат будущего артефакта.

Настоящий synthetic roundtrip уже проверен: Python/PostgreSQL 18 source →
encrypted archive → MinIO HTTPS/SigV4 → другой restore-контейнер; SHA-256 файлов,
row count и row digest совпали. Проверен реальный keyfile helper с сохранением
чужих ключей и ограничивающих options. Это не внешняя приёмка всех ОС/провайдеров.

**Запущенная установка и рабочее дерево отличаются.** Последние C1/C2 миграции
и изменения UI/worker ещё не были развёрнуты на текущей установке. Живое исправление
Telegram было конфигурационным: точное разрешение `api.telegram.org:443` в workspace
и повтор уже существующего теста. Токен не менялся и не печатался.

Рабочее дерево содержит много незакоммиченных изменений, включая созданные ранее.
Не сбрасывать их, не выбирать старый HEAD как будто это текущая проверенная версия.
Коммиты, теги, публикация и обновление работающей установки этим планом не разрешены.

## 3. Границы Beta

Включить A, B и подтверждённые профили C1/C2. D не является условием релиза.
Из E выполнить необходимые для выпуска операции: упаковку, установку/обновление,
backup/recovery, контроль состояния, документацию и ручную приёмку.

Ограничения C2 должны быть видны до настройки и запуска:

- Собственный bounded manifest/gzip/AES-256-GCM engine, не restic/Borg.
- До 16 MiB данных, 1000 файлов, 8 каталогов/8 БД; каталоги только `/srv`,
  ограниченные имена; пустые каталоги, ownership и исходные permissions не сохраняются.
- PostgreSQL: логический pg_dump, физический размер одной БД до 64 MiB,
  major клиента соответствует серверу. Не копировать работающий PGDATA/SQLite.
- Заявленный кодом профиль: Ubuntu 22.04/24.04, Debian 12/13, Python 3.10–3.13,
  PostgreSQL 14–18, amd64/arm64. **Официальная Beta-матрица включает только реально
  проверенные комбинации.** Непроверенные комбинации маркировать experimental
  или сузить поддержку; не расширять её по аналогии.
- Один активный C2 executor глобально, ограниченные попытки/таймауты, single PUT.
  Retention только own exact keys; версии versioned bucket не purged.
- SUCCESS upload не равен restore. FILES_VERIFIED не равен PostgreSQL restore.
  RESTORED не подтверждает работоспособность всего приложения и cluster globals.
- C1 rotation управляет стандартным authorized_keys текущего пользователя,
  требует Python; копии ключей в других SSH key sources не отзываются автоматически.

Предпочтительный путь: закрыть критическую приёмку C на отдельном стенде до Beta.
Если стенда нет, не объявлять C принятым. Подготовить вариант внутреннего пилота
с C как experimental, явным opt-in и запретом исполнения по умолчанию на серверной
стороне и в runner. Такого общего feature gate сейчас нельзя предполагать:
при выборе этого пути его необходимо реализовать и проверить, а не ограничиться
предупреждением в README. Изменение состава публичной Beta согласовать с владельцем.

## 4. Порядок выполнения

### P0. Аудит текущего кандидата

1. Прочитать AGENTS.md, README, brief, status/roadmap и все матрицы приёмки.
2. Сверить весь текущий diff и новые файлы с реализацией. Проверить C1/C2 не только
   по документации и прежним зелёным тестам; исправлять обнаруженные дефекты.
3. Отдельно проверить очереди/leases/locks, отзыв прав между enqueue и исполнением,
   фазами SSH rotation и записью результата; crash после remote effect до DB commit.
4. Проверить SSRF/DNS/TLS, safe keyfile updates, resource limits, recovery-key custody,
   restore-target isolation, archive integrity и секреты в HTML/logs/reports/images.
5. Обновить честную таблицу «готово / проверено изолированно / внешний блокер».

Результат P0: понятный состав кандидата, список дефектов и release blockers.
Не начинать с version bump и публикации образов.

### P1. Закрыть приёмку поддерживаемого профиля C

Только отдельные синтетические цели с разрешением владельца:

- C1: чистый сервер с Docker и отдельно без Docker; install/bootstrap, метрики,
  история, STOP/restart, сеть down/up, retry, disable/revoke, отказ старому SSH-ключу
  после проверенного нового login. Сохранить чужие keys/options, проверить конфликты
  keyfile и прерывание между add/verify/revoke/DB commit.
- C2: несколько серверов/хранилищ проекта, synthetic S3 probe в своём prefix,
  ручной запуск и реальное schedule, конкурентные задания/runner, S3 down/up,
  queued/running cancel, runner restart, bounded retries, отзыв роли/связи/SSH.
- Реальный archive из fixture-файлов и PostgreSQL БД загрузить в согласованное S3,
  восстановить на другом одноразовом host, сравнить hashes/rows/digests.
- Подтвердить, что retention не удаляет чужой fixture-объект, а удаление InfraDeck
  записи не удаляет сервер/архивы; активные задания блокируют удаление.
- Проверить уведомление о реальном синтетическом инциденте и восстановлении через
  разрешённый тестовый Telegram-канал. Наличие test-message не заменяет этот сценарий.

Результат P1: заполненные C1/C2 матрицы с датой, окружением и доказательствами.
Необязательные для выбранного пилота B providers оставить отдельно непринятыми;
если они заявлены поддерживаемыми для публичной Beta — нужна их реальная приёмка
или явная маркировка experimental. Не скрывать открытые B пункты за общим PASS.

### P2. Упаковка релиза и минимальная эксплуатационная готовность

1. Подготовить один согласованный номер `0.5.0-beta.1`: package/lockfile,
   Compose image references, About/UI, scripts, release manifest и документация.
   Найти все фактические источники версии; не выполнять слепую замену `0.1.0`.
2. Собрать web/worker/runner/migrate из одной ревизии. Runner может использовать
   worker image, но manifest должен точно указывать этот контракт. Зафиксировать
   теги и digest, совместимые ОС/архитектуры, Node/PostgreSQL/Redis версии.
3. Проверить installer/update для выбранного пути. Для удобной публичной Beta
   подготовить Compose с опубликованными pinned images, чтобы на целевом host
   требовался Docker/Compose, а не Node/npm или сборка исходников. Текущий
   поддерживаемый npm/source-build путь сохранить и честно документировать.
4. Проверить пустой setup, отсутствие demo/default passwords, сохранение secrets
   при повторной установке; одноразовый OWNER init отдельно от обычного setup.
5. Проверить migration gate перед всеми приложениями и upgrade копии старой БД
   с сохранением пользователей, финансов, истории, ciphertext и старых отчётов.
6. Сделать metadata backup и настоящий restore в отдельную установку. Отдельно
   проверить ENCRYPTION_KEY, report artifacts и доступность зашифрованных credentials.
   Не обещать DB rollback откатом только Docker image; записать recovery procedure.
7. Проверить HTTPS URL/reverse proxy, cookie/session/origin, закрытые DB/Redis,
   отсутствие Docker socket, права файлов/volumes, healthchecks и перезапуск services.
8. Проверить длительную работу, очередь/ретенцию/диск и отказ/recovery компонентов;
   конкретные длительность и объём стенда записать, не выдавать smoke за load test.
9. Проверить runtime advisories, лицензии/SBOM и соответствующий SOURCE_URL/AGPL.
   Исключить `.env`, data, credentials, dumps, traces и private inventory из build
   context/образов/артефактов. Нулевой npm audit не равен полному security audit.

Результат P2: проверяемый комплект образов/manifest/Compose и установка по README.
Публикация в registry и обновление рабочих сервисов — отдельные действия после
предъявления конкретного кандидата владельцу.

## 5. Условия Go / No-Go

**Go для выбранной Beta:** все блокирующие P0–P3 проверки пройдены на выпускаемом
артефакте; чистая установка и upgrade/isolated recovery воспроизводимы; секреты
не утекли; заявленные операции C приняты либо реально закрыты experimental gate;
ограничения и внешние неподтверждённые B providers явно перечислены.

**No-Go:** потеря/утечка credentials, cross-workspace/RBAC bypass, отзыв старого SSH
до нового доступа, изменение чужих key entries/S3 objects, запись restore поверх
production, неограниченные/дублирующиеся remote effects при retry/crash, потеря
истории/артефактов, неподтверждённый backup/recovery приложения, невоспроизводимые
образы/миграции или автоматическое включение экспериментальных операций.

Номер версии и наличие новой функциональности не заменяют эти условия.

## 6. Что потребуется от владельца

- Разрешённые source host и другой disposable restore host; ОС/архитектура,
  PostgreSQL major, SSH user/port и пределы разрешённых тестов.
- S3 HTTPS endpoint, region, bucket, отдельный synthetic prefix и локальная
  настройка минимальных credentials; не пароль/private key в переписке.
- Разрешённый тестовый Telegram chat для incident/recovery; SMTP/Discord и другие
  providers только если включаются в принимаемую матрицу.
- Целевой host/домен, путь registry/repository, доступность amd64/arm64, предпочтение
  внутренней или публичной Beta. Не выдумывать registry, домен или credentials.

Отсутствие этих данных не останавливает изолированные P0/P2/P3 работы. Зависимые
внешние шаги остаются конкретными блокерами; не тестировать вместо них рабочий сервер.
