# Руководство пользователя InfraDeck

Обновлено 22.10.2026. SSH/Sentinel подключается из карточки сервера;
backup runner остаётся будущей возможностью.
Установка и восстановление администратора: [README](../README.md), [operations](operations.md).

## Проекты и серверы

1. Войти под OWNER/ADMIN. В «Проекты» создать проект с уникальным кодом.
2. В «Инфраструктура» добавить ресурс типа SERVER, заполнить известные характеристики
   и выбрать проект. Ручная запись не устанавливает ничего на сервере.
3. В карточке ресурса привязать остальные проекты, если сервер общий. Один проект
   может содержать несколько серверов, БД, приложений и S3-ресурсов.
4. S3 в реестре остаётся учётной записью. Реальное исполнение настраивается
   отдельно в `/backups`: [C2 руководство](backups-s3.md), [engine/лимиты](backup-engine.md).
   Не вводить access/secret keys в заметки ресурса. Manual result не запускает бэкап.

Архивирование и удаление записи различаются. Удаление никогда не удаляет сервер
или внешнее хранилище; активные проверки/привязки требуется отключить заранее.
История и последствия: [deletion.md](deletion.md).

Действия с ресурсом находятся сразу под названием: «Редактировать» открывает
диалог с текущими данными, «Архивировать» меняет состояние записи. «Удалить навсегда»
находится в меню «Опасные действия». Меню и диалоги закрываются Escape; опасное
удаление по-прежнему требует всех подтверждений и проверки зависимостей.
Управление SSH/Sentinel остаётся отдельно в блоке управления сервером.

Для удаления недостаточно одного названия: требуется также обязательный флажок
подтверждения удаления связей и сохранения истории. Активные зависимости блокируют
удаление независимо от этих подтверждений.

## Пользователи и проектные права

1. В «Доступы» создать приглашение VIEWER/OPERATOR с флагом «Только назначенные
   проекты». Передать одноразовую ссылку получателю; SMTP для этого не требуется.
2. В «Проектные права и бюджеты» назначить пользователю проекты и проектную роль.
   Для существующего VIEWER/OPERATOR можно переключить область доступа с workspace
   на назначенные проекты. OWNER/ADMIN workspace сначала нужно понизить в роли.
3. Ограниченный пользователь после входа попадает в `/my-projects`, видит только
   назначенные проекты, ресурсы и их долю расходов. Без назначений список пуст.
4. Общие host-метрики разрешаются отдельным флагом: они могут раскрывать нагрузку
   соседних проектов на том же сервере. Внешние каналы настраивает администратор.
5. Проектный OPERATOR может подтверждать инциденты сервера, если имеет OPERATOR
   во всех проектах, связанных с этим сервером. Для host-инцидентов дополнительно
   нужен доступ к метрикам. VIEWER не может подтверждать инциденты.

Проектный портал намеренно не открывает общий реестр, imports, audit, credentials,
историю удаления и workspace-отчёты. Экспорт из проектного портала пока не поддержан,
даже при старом canExport. API-токены текущей read API предназначены для workspace
администраторов. Отзыв проекта действует на следующий запрос; сервер проверяет
актуальные назначения, а не только cookie. Обычные старые workspace-права сохранены.

## Расходы и бюджет

1. В «Расходы» внести месячную стоимость ресурса, валюту, даты действия и признак
   плановой записи. В дополнительных записях распределить стоимость по проектам
   через проценты. Связь с проектом сама по себе не распределяет стоимость.
2. Открыть «Проектные права и бюджеты», выбрать месяц UTC, добавить бюджет и валюту.
   Бюджет является лимитом, не расходом. Можно редактировать/удалить его; прежнее
   значение сохраняется в аудите, при удалении проекта также в историческом снимке.
3. Расчётные расходы периода используют неплановые effective-dated месячные ставки
   и доли allocations, пропорционально времени действия в месяце UTC. Это оценка,
   не бухгалтерский факт оплаты. Остаток = бюджет минус расчётные расходы.
4. Валюты раздельны; отсутствующий бюджет не равен нулю. Нераспределённая доля общего
   ресурса не приписывается каждому проекту. За 80/100% бюджета создаются WARNING /
   CRITICAL; снятие превышения/удаление лимита/смена периода закрывают сигнал.

Новые отчёты содержат бюджеты текущего месяца и сводку метрик; бюджет относится ко
всему проекту, всем средам, независимо от environment-фильтра отчёта. Старые файлы
остаются неизменными. Общие финансовые ограничения: [reports.md](reports.md).

## Подключение метрик

Вариант без ручной установки сборщика: [SSH и управляемый Sentinel](managed-servers.md).
Создайте ключ в карточке SERVER, разрешите первоначальный SSH-доступ, подтвердите
host key и установку. Docker при отсутствии устанавливается только с отдельным
разрешением. Доступны CPU/RAM/load и заполнение `/`, графики CPU/RAM до 24 часов.

### Существующий Prometheus

Нужны доступный из worker Prometheus-compatible API и node_exporter на Linux-хостах.
Этот альтернативный профиль не устанавливает Prometheus/node_exporter автоматически.
Оператор устанавливает сборщик по [официальной инструкции](https://prometheus.io/docs/guides/node-exporter/).
Ограничить его доступ сетью мониторинга; не публиковать метрики без защиты.

Пример конфигурации существующего Prometheus (адрес заменить своим):

```yaml
global:
  scrape_interval: 30s
scrape_configs:
  - job_name: node
    static_configs:
      - targets: ["SERVER_PRIVATE_IP:9100"]
```

Retention и лимит диска на стороне Prometheus задаёт оператор, стартовый ориентир
30 дней. InfraDeck не устанавливает эту конфигурацию и не управляет retention Prometheus.

1. В разрешённых целях проверок добавить hostname Prometheus и порт, например
   `prometheus:9090`. Для внутреннего адреса явно разрешить private network.
   `localhost` внутри Docker означает сам контейнер, а не хост пользователя.
2. Открыть «Метрики серверов», добавить базовый URL API, например
   `http://prometheus:9090`. Authorization необязателен; с credentials нужен HTTPS
   и доверенный TLS-сертификат. Не помещать пароль в URL.
3. Выбрать источник, сервер и точные значения `job` и `instance` из Prometheus.
   Эти значения ограничивают все встроенные запросы; произвольного PromQL в UI нет.
4. Через минуту проверить CPU, RAM через MemAvailable, файловые системы/inodes,
   load15 на CPU, iowait, суммарные RX/TX B/s без loopback.
5. Выбрать сервер/метрику/период 1, 6, 24 или 168 часов. График читается из реальной
   истории источника. При отсутствии истории не строится выдуманный baseline.

Последняя сводка хранится в PostgreSQL, не весь time series. Значения старше
180 секунд считаются STALE. Ошибка источника даёт UNKNOWN, отсутствие части рядов
PARTIAL; это не означает, что нагрузка нулевая. Новые записи не считаются подключёнными
без успешного ответа. Отказ сбора дольше двух минут создаёт отдельный инцидент.

## Правила, TLS и обслуживание

- В «Метрики серверов» создать правило: сервер, метрика, порог, длительность,
  порог и длительность восстановления, severity. Проценты и B/s не взаимозаменяемы.
- Пример диска: >70% в течение 900 секунд; восстановление <65% 600 секунд.
  CPU: >80% 600 секунд; RAM: >85% 600 секунд. Критичные правила добавить отдельно.
- Короткий пик не создаёт firing. Исчезновение ряда не считается восстановлением.
  После разрыва наблюдений выдержка начинается заново; открытый инцидент сохраняется.
- Правило можно отключить или подавить до даты UTC, максимум 30 дней. Пустая дата
  снимает подавление. Напоминания выключены по умолчанию; при включении не более
  трёх на эпизод, не чаще раза в час. Предупреждение того же показателя подавляется
  при активном CRITICAL; статусы инцидентов при этом остаются видны.
- Для обслуживания создать окно ресурса в дополнительных записях. В это время
  сбор продолжается, новые host-сигналы не рассылаются; отложенные сообщения ресурса
  отменяются. ACK не равен исправлению проблемы и не отключает сбор.
- TLS: добавить hostname/port и ресурс, разрешить цель. Проверка каждые 15 минут,
  warning <30 дней, critical <7. Цепочка и имя проверяются; неуспешная проверка
  отображается UNKNOWN с инцидентом, а не как действующий сертификат. Свежесть TLS
  в UI ограничена часом. SMTP/STARTTLS этим монитором не проверяются.
- Для существующих backup-политик проверка свежести включается отдельно в этом же
  разделе. Используется последнее завершённое SUCCESS и freshnessHours политики.
  Ручные старые политики не получают новые фоновые проверки без включения.

OOM, SMART/RAID, температура, Docker, PostgreSQL replication/locks, процент сетевого
канала и прогноз заполнения пока не собираются встроенным профилем. Для них можно
передавать подходящие оповещения через Alertmanager при наличии внешнего источника;
указание этих показателей в roadmap не означает готовый сборщик.

## Email, Telegram и Discord

1. В «Каналы уведомлений» выбрать проект, типы событий и минимальную severity.
2. Email: SMTP host, 465 (TLS) либо 587 (обязательный STARTTLS), пользователь/пароль,
   from и один to. Telegram: bot token и числовой chat ID доступного боту чата.
   Discord: incoming webhook URL канала `https://discord.com/api/webhooks/...`.
3. Явно разрешить сетевую цель worker: SMTP host:port, `api.telegram.org:443` либо
   `discord.com:443`. Private network только для намеренно выбранного SMTP.
4. После сохранения канала нажать «Протестировать подключение» (EN: Test connection).
   Тестовое сообщение отправляется через worker для Telegram, Discord и email.
   «Последний тест» и журнал доставок обновляются автоматически: очередь, принято
   провайдером, ошибка или отмена. Постановка в очередь не означает доставку;
   проверьте само сообщение во внешнем канале. Отправка выполняется только по кнопке.
   До настройки никаких писем/сообщений приложение самостоятельно не отправляет.

Credentials шифруются и не возвращаются на странице, в отчёте или журнале.
Для замены credentials отключить канал и создать новый; старые события останутся
в журнале. Администратор отвечает за состав внешнего чата: он может отличаться от
проектных пользователей InfraDeck. Общий сервер отправляет свои события в явно
настроенные каналы связанных проектов, но не называет соседние проекты.

Состояния QUEUED / SENT / FAILED / CANCELLED. SENT означает принятие провайдером,
не прочтение. Максимум 5 попыток, backoff/jitter и Retry-After; FAILED можно повторить
вручную. Сообщения одного ресурса/канала группируются в пределах лимита 1800 символов,
не чаще отправки раз в 5 секунд. Сетевой сбой после принятия может дать внешний дубль:
доставка at-least-once. Отзыв канала/issuer или удаление привязки отменяет очередь.
SENT/CANCELLED очищаются через 30 дней; FAILED хранятся до отдельной операторской
очистки. Credentials каналов и журнал входят в metadata backup; ENCRYPTION_KEY
сохраняется отдельно. При потере ключа нужно пересоздать подключения.

## Alertmanager

1. В «Метрики серверов» создать Alertmanager-подключение к конкретной привязке,
   задать срок UTC (до года), сохранить показанный один раз Bearer token.
2. В существующем Alertmanager использовать endpoint из результата и конфигурацию:

```yaml
webhook_configs:
  - url: https://INFRADECK/api/integrations/CONNECTION-ID/alertmanager
    send_resolved: true
    http_config:
      authorization:
        type: Bearer
        credentials_file: /run/secrets/infradeck-alertmanager-token
```

В каждом alert labels `job`/`instance` должны точно совпадать с привязкой.
До 50 alerts и 64 KiB на запрос; при больших группах разбивать на отправителе.
Повторы не создают повторный инцидент/доставку; старое firing после resolved
того же startsAt не открывает его снова. Есть expiry, отзыв и лимит 60 запросов/мин.
Для ротации создать новое подключение и отозвать старое. За пределами локального
теста обязательны HTTPS и защищённый ingress. Raw annotations и payload не сохраняются.

## Диагностика и границы

- Ошибка входа: проверить email и новый пароль, не старый файл E2E credentials.
- Нет метрик: heartbeat worker, allowlist/DNS, URL API, job/instance, scrape target UP,
  наличие node_exporter рядов и синхронизацию времени.
- Нет уведомления: severity/тип/проект, maintenance/silence, включённый канал,
  актуальные права создателя, allowlist, TLS и журнал доставок.
- Сам отказ всего InfraDeck нельзя надёжно сообщить из упавшего InfraDeck:
  нужен независимый внешний health-check.
- SSH, firewall, выполнение бэкапов/restore и установка обновлений не входят в
  реализованный B. Для приёмки реальной доставки нужны согласованные тестовые
  email/chat/webhook, для продуктовых коннекторов нужны выбранные продукты/API.

Контракты проверялись по [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/),
[Nodemailer SMTP](https://nodemailer.com/smtp), [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage),
[Discord webhooks](https://docs.discord.com/developers/resources/webhook).
